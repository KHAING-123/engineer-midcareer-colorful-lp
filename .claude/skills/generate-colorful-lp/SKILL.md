# generate-colorful-lp

現在の `frontend/` の Colorful LP を `output/` 配下へ複製し、指定した Customer Input の**見出し・説明文(14項目)**の変更を**生成先の `lpContent.js` だけ**に反映して、独立して `npm ci`・Build・起動できるかを確認する。

## 呼び出し方

```
/generate-colorful-lp <Inputファイル> <出力先>
```

例:

```
/generate-colorful-lp docs/04-customer-input-test.md output/colorful-input-test
/generate-colorful-lp docs/tests/colorful-text-input-test.csv output/colorful-csv-test
```

- Input は **Markdown(`.md`)** または **CSV(`.csv`)**。拡張子で入力形式を決める(`.md` は従来どおり、`.csv` は下記「CSV入力の場合」)。

- 引数は `$ARGUMENTS` で受け取る。1つ目が Input ファイル、2つ目が出力先。
- どちらかが欠けている場合は、実行せず停止して引数を確認する。

## 位置づけ

- Input の文章を LP に反映する機能の、**文章対応範囲を広げた限定版**である。反映できるのは下記の14項目の**値(文字列)だけ**。
- 14項目以外の実データがInputで変わっていれば、生成前に停止して報告する(自動で対応しない)。
- `frontend/` は参考元として維持し、変更しない。既存の出力フォルダも変更しない。
- Commit・Push はしない。

## 対応する14項目

`frontend/src/data/lpContent.js` のキーと、Input 内の読み取り位置(`docs/02-customer-input.md` の書式。対応の根拠は `docs/06-input-mapping.md`)。

| # | キー | Input の節 | Input の書式 | `\n` の扱い(06 の凡例) |
|---|---|---|---|---|
| 1 | `membersSection.title` | 6. 01 MEMBERS | 「### 見出し」のコードブロック | 候補(`<wbr>`。幅が足りないときだけ改行) |
| 2 | `membersSection.lead` | 6. 01 MEMBERS | 「### 説明文」のコードブロック | 強制(`pre-line`) |
| 3 | `jobsSection.title` | 7. 02 OUR WORK | 「### 見出し」のコードブロック | 強制 |
| 4 | `jobsSection.lead` | 7. 02 OUR WORK | 「### 説明文」のコードブロック | 強制 |
| 5 | `growthSection.title` | 8. 03 GROWTH STEP | 「### 見出し」のコードブロック | 強制 |
| 6 | `growthSection.lead` | 8. 03 GROWTH STEP | 「### 説明文」のコードブロック | 強制 |
| 7 | `supportSection.title` | 9. 04 SUPPORT | 「- 見出し：」の1行 | 強制 |
| 8 | `supportSection.lead` | 9. 04 SUPPORT | 「### 説明文」のコードブロック | 強制 |
| 9 | `careersSection.title` | 10. 05 CAREER PATH | 「- 見出し：」の1行 | 強制 |
| 10 | `careersSection.lead` | 10. 05 CAREER PATH | 「- 説明文：」の1行 | 強制 |
| 11 | `interview.title` | 11. 06 INTERVIEW | 「- 見出し：」の1行 | 強制 |
| 12 | `interview.lead` | 11. 06 INTERVIEW | 「### 説明文」のコードブロック | 強制 |
| 13 | `selectionSection.title` | 12. 07 FLOW | 「- 見出し：」の1行 | 強制 |
| 14 | `selectionSection.lead` | 12. 07 FLOW | 「- 説明文：」の1行 | 強制 |

読み取りの規則:
- **改行コードの正規化(最初に行う)**: Input の `\r\n`(CRLF)を `\n`(LF)に正規化してから解析する。正規化するのは改行コードだけで、文章内容・空白・論理的な改行数(空行を含む)は変えない。CRLF の `\r` を値に残さない。単独の `\r`(CR だけの改行)は正規化せず、判断不能として扱う。
- **コードブロック**: 開始の ``` と終了の ``` の間の行を、行の区切りだけ `\n` に置き換えて1つの文字列にする。空行は `\n\n` になる。最後の行の後ろの改行は含めない。行頭・行末の空白は**削らない**。
- **1行書式**: 最初の全角コロン「：」の直後から行末までを、そのまま値とする。1行なので `\n` は含まれない。
- 項目の有無: 対象の見出し(「### 見出し」「### 説明文」)や行(「- 見出し：」「- 説明文：」)が節の中に**存在しない**ことと、存在するが値が読み取れない(コードブロックが無い、値が空など)ことは区別する(下記 4-1)。
- 「リスト見出し」「補足メッセージ」など、上表以外の見出し・文章は対象外(下記の「対応範囲外の差分」で照合する)。
- 現在値は、`frontend/src/data/lpContent.js` を実際に読み込んで得る(この表や過去の記載から推測しない)。上表のキーが `lpContent.js` に無い、または文字列でない場合は停止して報告する。

## 固定値

- リポジトリルート: `/workspaces/engineer-midcareer-colorful-lp`
- 複製元: `frontend/`
- 出力先: プロジェクト直下の `output/` 配下に限定する(例: `output/colorful-input-test`)。
- `package.json` の `name`(`engineer-rookie-lp`)は維持する。
- 既存素材(画像・未使用素材を含む)は削除しない。
- 対象外: `docs/archive/`、ZIP(触れない・複製しない)。
- 維持するもの: 画像、カード内容、リンク、色(`accent`・`circle`)、Section の順序、番号(`number`)、英字ラベル(`label`)。
- 変更してよいのは、生成先の `src/data/lpContent.js` の上記14項目のうち、**Input で変更された項目の値だけ**。

## 作業の流れ

### 0. 開始時刻を記録する(最初。資料を読む前)
- 資料やInputを読む**前に**、開始時刻を記録する(例: `date +%s` と `date`)。これが所要時間の開始点。
- 時間計測は `date +%s` の差だけで行う。`/usr/bin/time` など環境に無いことがあるコマンドは使わない(必須にしない)。
- 資料の読み込み時間も合計に**含める**。読み込みの完了時刻も記録する(手順2の終わり)。

### 1. 引数を検証する
次のいずれかに当てはまる場合は、何も作成せず停止して報告する。
- Input ファイルが存在しない、または `docs/archive/` 配下、ZIP である。拡張子が `.md` でも `.csv` でもない場合も同様に停止する。
- 出力先が `output/` 配下の直下の新しいフォルダではない(絶対パス、`..` を含む、`output/` 以外、`output` そのもの、`output/<名前>/<さらに下>` など)。
- 出力先が既に存在する(シンボリックリンクを含む)。**上書きせず停止**する。削除・別名での続行もしない。
- 出力先が `frontend/` 配下、または `frontend/` と同じ場所を指す。

### 2. 資料とSkillと指定Inputを全文読む
毎回、次を**全文**読む(前回の記憶に頼らない)。分割して読む場合も**最後の行まで**確認する(途中で止めない)。
- `docs/01-lp-reference.md`
- `docs/02-customer-input.md`
- `docs/03-lp-checklist.md`
- `docs/06-input-mapping.md`(キーと改行の扱いの根拠)
- この `SKILL.md`
- 指定された Input ファイル
- `frontend/src/data/lpContent.js`(現在値)
- Input が CSV の場合は、`scripts/read-csv-input.mjs` と `scripts/apply-changes.mjs` も読む。

読み終えた行数(特に指定 Input)を報告に記載する。`06` の記載が `lpContent.js` の実際のキーと食い違う場合は、停止して報告する。

### 3. 作業前の状態を記録する
次を、プロジェクト外のスクラッチパッドに保存する。
- `git status --short`(全体)
- `git status --short -- frontend`
- `git diff --stat -- frontend`
- `frontend/` のファイル一覧とハッシュ(`node_modules`・`dist` を除く)
- 既存の `output/` 配下の一覧とハッシュ(既存の出力を変更していないことの確認用)
- `docs/01〜03`・`docs/06` のハッシュ
- 使用中のポート(`ss -ltn`)

### 4. Inputと `lpContent.js` を照合する(生成前)

> **Input が CSV(`.csv`)の場合**は、この手順4(4-1〜4-4)の代わりに、下記「CSV入力の場合」の手順C-1〜C-3を行う。以降の手順5以降は共通(手順7・8は「CSV入力の場合」の記述に従う)。

**4-1. 14項目の判定**
14項目それぞれを、次の4つのどれかに分類する。

| 分類 | 条件 | 扱い |
|---|---|---|
| 同じ | Input の値が現在値と完全に一致する(改行の変換後。空白も含めて比較) | 変更しない |
| 変更 | Input に値があり、現在値と異なる | 反映対象にする |
| 未指定 | Input の該当の節に、その項目の見出し(「### 見出し」「### 説明文」)も行(「- 見出し：」「- 説明文：」)も**無い**(項目自体が無い) | 現在値を維持する。変更しない |
| 判断不能 | 下記のいずれか | 生成前に停止して報告する |

判断不能の例(1つでもあれば、複製・変更・`npm ci` を行わず停止):
- **見出しだけあり、値が無い**: 「### 見出し」「### 説明文」はあるが、続くコードブロックが無い(開始の ``` が無いまま次の見出しや節に移る)。項目自体が無い「未指定」とは区別し、停止する。
- **空**: コードブロックの中身が空、「見出し：」の後ろが空(空文字)、または**空白・改行だけ**(半角・全角スペース、タブ、空行だけ)の値。未指定と区別し、**削除とみなさない**。意図(削除か、記入漏れか)が分からないため、確認が必要として報告する。空白・改行だけの値を「変更」として反映しない。
- 同じ項目が Input 内に複数ある、または複数の読み方ができる。
- 差が**空白(行頭・行末・全角半角)だけ**で、意図が分からない。
- コードブロックの閉じ忘れなど、書式が読み取れない。
- 1行書式の項目で、現在値に `\n` があり改行位置が判断できない。

**4-2. 改行の扱い**
- Input の改行(CRLF は LF に正規化した後)は、そのまま `\n` に対応させる。Skill が改行を**追加・削除・整形しない**。論理的な改行数(空行を含む)も変えない。
- 行数が変わる変更では、報告に「`\n` の扱い(強制/候補)」と、改行数の増減を記載する。強制改行の項目は、Input の改行が画面でも改行になる。見え方はブラウザで未確認とする。

**4-3. 対応範囲外の差分**
- 14項目以外の**実データ**(番号・英字ラベル、カードの文章、タグ、alt、期間、URL、画像パス、色、補足メッセージ、`hero`・`opening`・`header`・`footer`・`finalCta`・各配列の中身・並び順など)を、`lpContent.js` の対応する値と照合する。
- 対応の目安は、Input 各節の「対応データ」(例: `jobsSection` / `jobs`)と、`06` の対応表に従う。
- 比較時の正規化:
  - Input のコードブロック内の実際の改行は、`lpContent.js` の `\n` に対応する。
  - 画像パスは拡張子の違いを無視する(Input の「設定パス。実体は .svg」などの注記は比較対象外)。
  - 「設定なし」「コメントアウトされている」「使用しない」と書かれた項目は、`lpContent.js` で同様に未設定・コメントアウトであることを確認する。
  - 「15.〜18.」の解説、確認状況、今後決める事項の節は、`lpContent.js` との比較対象ではない。
- **対応範囲外の実データに差分が1つでもあれば、生成前に停止**し、次を報告する。複製・変更・`npm ci` は行わない。
  - 差分の場所(Input の節・行、`lpContent.js` のキー)
  - Input の値と `lpContent.js` の値
- 照合できなかった項目(判断できない記述)がある場合も、停止して報告する。推測で補わない。

**4-4. 結果の確認**
- 14項目の分類(同じ/変更/未指定/判断不能)を一覧にする。判断不能が0件で、範囲外の差分が0件のときだけ次へ進む。
- **全項目が「同じ」または「未指定」(変更0件)でも停止しない。** 内容を維持した LP として生成する(手順7をスキップし、手順8の差分は 0 とする)。

### 5. 出力先を再確認する
- 手順4を通過した後、出力先が存在しないことを再確認する。存在する場合は**上書きせず停止**する。

### 6. `frontend/` を複製する
`rsync -a` に除外リストを渡して複製する(`cp -r` 後の削除はしない)。

複製するもの:
- `package.json`、`package-lock.json`、`vite.config.js`、`index.html`、`.gitignore`
- `public/`
- `src/` 全体(`assets/images`、`assets/images-optimized`、README.txt、未使用素材を含む)

複製しないもの:
- `node_modules`、`dist`
- `*.zip`
- `.git`
- `*.log`、`.DS_Store`

複製後、除外対象が出力先に含まれていないことを確認する。

### 6-2. 複製直後の一致確認(Input反映の前)
この時点では、出力先は複製元と**完全に一致**しているはずである。
- `diff -rq frontend/src <出力先>/src` で差分がない。
- `package.json`、`package-lock.json`、`vite.config.js`、`index.html`、`.gitignore`、`public/` も一致する。
- 差分がある場合は、内容を報告して停止する(Input の反映に進まない)。

### 7. Inputを生成先の `lpContent.js` だけに反映する
変更が0件の場合は、この手順を行わない。

- 変更するのは `<出力先>/src/data/lpContent.js` の、**手順4で「変更」と分類した項目の値だけ**。「同じ」「未指定」の項目は書き換えない。
- 項目ごとに、該当ブロック(`membersSection` など)の 4 スペースインデントの `title:` / `lead:` 行を、**1行ずつ**置き換える。
  - 置き換え前に、そのブロック内で対象行がちょうど1つだけ見つかることを確認する(`interview` ブロックには、`topics[].title`(8スペースインデント)など別の `title:` があるので、取り違えない)。
  - キー、行末のカンマ、前後のコメント、他の行は変更しない。
- 値の書き方は、既存と同じシングルクォートの1行の文字列にする。改行は `\n`、`\` は `\\`、`'` は `\'` に変換する。
- 画像・カード・リンク・色・Section の順序・番号・英字ラベルは変更しない。
- `frontend/` 側の `lpContent.js` は変更しない。

### 8. Input反映後の差分確認(手順6-2とは別に行う)
次をすべて確認する。
- `diff -rq frontend/src <出力先>/src`: 差分が `src/data/lpContent.js` **だけ**(変更0件のときは差分なし)。
- `diff frontend/src/data/lpContent.js <出力先>/src/data/lpContent.js`: 差分の行が、**「変更」と分類した項目の行だけ**(1項目につき 1行が置き換わる)。他の行に差分がない。
- 両方の `lpContent.js` を Node で読み込み、キーごとに比較する(ESM の `import` を使う)。値が異なるキーの集合が、「変更」と分類した項目の集合と**完全に一致**する。14項目のうち「同じ」「未指定」の項目の値は変わっていない。
- 変更した各キーの値が、Input から得た値と一致する。
- 設定ファイル、`index.html`、`public/` が複製元と一致したままである。
- 想定外の差分があれば、内容を報告して停止する(`npm ci` に進まない)。

### 9. 依存導入とBuild
出力先で順に実行する。各コマンドは単独で実行し、終了コードを確認する(`time` などのラッパーを付けない。パイプを使う場合は `PIPESTATUS` などでコマンド本体の終了コードを確認する)。
1. `npm ci` — **通常は1回だけ**。同じ出力先で再実行しない。
   - **失敗した場合は、その時点で停止する。Build(手順9-2)・開発サーバー(手順10)には進まない。** 出力をそのまま報告し、原因を報告したうえで再実行するかを判断する。
2. `npm run build`(Input反映後、かつ `npm ci` が成功した場合だけ行う)
   - 失敗した場合は、その時点で停止し、開発サーバー(手順10)には進まない。

`npm ci` 成功後だけ Build を行い、Build 成功後だけ開発サーバーを起動する。失敗した場合は、出力をそのまま報告して停止する。修正のために `frontend/` や出力先のコードを変更しない。

### 10. 開発サーバーを起動する
- **`npm run build` が成功した場合だけ**行う。`npm ci` または Build が失敗していたら、起動せず手順9の停止・報告に従う。
- 空いているポートを選ぶ(手順3で記録したポート一覧と `ss -ltn` で確認。例: 5173 から順に探す)。
- `npm run dev -- --port <選んだポート> --strictPort` をバックグラウンドで起動する。
- **既存のサーバーは停止しない**(以前の出力のサーバーを含む)。
- `curl` などで HTTP 応答(ステータスコード)を確認する。
- Preview 用のポートを報告する。
- 配信される `lpContent.js` に、変更した項目の値が含まれることを確認してよい(ブラウザ表示の確認ではない)。

### 11. 元データが変更されていないことを確認する
- 作業後に、手順3と同じ内容を取得し、作業前と比較する。
  - `frontend/`: `git status --short -- frontend`、`git diff --stat -- frontend`、ファイル一覧とハッシュ
  - 既存の `output/` 配下(今回の出力先を除く): 一覧とハッシュ
  - `docs/01〜03`・`docs/06`、Input のハッシュ
- 作業前から存在した変更(例: `frontend/engineer-opportunity.zip` の変更)は「作業前から存在」と区別して報告する。
- 新しい差分があれば、その内容を報告する。
- ZIP、`docs/archive/` に変更がないことも確認する。

### 12. 時間を記録して報告する
各区間を記録する(`date +%s`)。
- 開始(手順0。**資料読込前**)
- 資料・Input 読込完了(手順2)
- 照合完了(手順4)
- 複製・Input反映・差分確認完了(手順8)
- `npm ci` 完了、Build 完了(手順9)
- 開発サーバー応答確認(手順10)

**合計時間は、手順0の開始から手順10の応答確認まで**とし、資料の読み込み時間を含める。資料読込の所要時間も別に報告する。ブラウザでの目視確認の時間は含めない。

報告に含めるもの(事実と確認状況を分ける):
- 使用した Input と出力先、各資料と Input を最後まで読んだ行数(CSV の場合は、スクリプトの検証結果の要約と、CSV のBOM・改行コード・末尾改行の有無を含む)
- 14項目の分類(同じ/変更/未指定/判断不能)と、変更した項目の「変更前→変更後」、`\n` の扱い(強制/候補)
- 範囲外の実データの差分の有無
- 複製直後の一致確認の結果(手順6-2)と、Input反映後の差分確認の結果(手順8)
- `npm ci`(実行回数)・`npm run build` の結果(成功・失敗、警告)
- 開発サーバーのポートと HTTP 応答
- `frontend/` と既存の出力に新しい変更がないかの結果
- 各区間の時間と合計時間
- 現在の状態として維持したもの:
  - 仮リンク: `https://example.com/entry`、`https://example.com/privacy`、`https://example.com/terms`

## CSV入力の場合

入力表の様式は `docs/09-spreadsheet-input-guide.md`、雛形は `docs/templates/colorful-text-input.csv`。CSV の解析・検証は **スクリプトで行い、Claude の目視判断だけに依存しない**(スクリプトの判定を、そのまま採用する)。

- 依存パッケージなし(Node 標準のみ)。CSV の文字列は**データとして扱い、コードとして実行しない**。
- CSV には 14項目(`title`・`lead`)だけが含まれる。Markdown 入力の「対応範囲外の差分の照合(4-3)」は、CSV には範囲外のデータが無いため行わない。
- 手順0・1・2・3・5・6・6-2・9・10・11・12(時間計測、引数検証、資料の読込、作業前の記録、出力先の確認、複製、Build・起動、元データの確認、報告)は、Markdown 入力と同じ。

### C-1. CSV を読み取り・検証する(手順4の代わり。出力先を作る前)
```
node .claude/skills/generate-colorful-lp/scripts/read-csv-input.mjs <CSVファイル> --out <スクラッチパッド>/plan.json
```
- `--out` の保存先は、プロジェクト外のスクラッチパッドにする。標準出力にも同じ JSON が出る。
- 終了コード 0 = 検証成功、1 = 検証エラー、2 = 使い方の誤り。
- スクリプトが行う検証(すべて満たさないと `ok: false`):
  - UTF-8(先頭 BOM の有無どちらも可)。不正なバイト列はエラー。
  - LF・CRLF・末尾改行なしのどれも可。セル内の CRLF は LF に正規化する。単独の CR はエラー。
  - 引用符内のカンマ・二重引用符(`""`)・セル内改行を、状態機械の CSV パーサーで読む(行分割・カンマ分割は使わない)。閉じていない引用符、引用符なしセル内の `"`、閉じ引用符の直後の不正な文字はエラー。
  - ヘッダーが `項目ID,セクション,項目名,操作,入力内容,備考` の6列であること。
  - データが14件で、各行が6列であること。空行はエラー。
  - 項目IDが、14項目(上表のキー)と重複・欠落・不明なく一致すること。**行の並び順には依存せず、項目IDで対応させる。**
  - 操作が「維持」「変更」のどちらかであること(前後の空白があってもエラー)。
  - 「変更」の入力内容が、空・空白だけ・改行だけ(全角空白・タブを含む)ならエラー。
  - 文章の前後の空白・改行は削除しない。
- 値の決め方:
  - 「維持」：**生成時の frontend の現在値**を使う。入力内容が違っても反映しない(警告 `keep-input-ignored` が出る)。
  - 「変更」：入力内容をそのまま使う。現在値と完全に同じなら「同じ」(書き換えない)。
  - 反映する「変更」の一覧は、JSON の `changes`(`id`・`from`・`to`)。
- `セクション`・`項目名` 列が想定と異なる場合は警告(`section-differs`・`label-differs`)。反映には使わない。

### C-2. 検証結果の扱い(停止条件)
- `ok: false`(終了コード 1)の場合は、**出力フォルダを作らず、複製・`npm ci` も行わず停止**し、`errors`(コード・メッセージ・項目ID・行)をそのまま報告する。Claude が推測で補ったり、エラーを無視して進めたりしない。
- `ok: true` のときだけ、手順5(出力先の再確認)以降へ進む。
- 報告する内容：`counts`(維持・変更の件数)、`changes`(項目ID・変更前→変更後)、`warnings`、`file`(BOM・改行コード・末尾改行の有無)、`\n` の扱い(強制/候補。`membersSection.title` だけ候補)と改行数の増減。
- `changes` が0件でも停止しない(内容を維持した LP として生成する。手順7は行わない)。

### C-3. 生成先へ反映する(手順7・8の代わり)
手順6・6-2で複製したあと、次を実行する。
```
node .claude/skills/generate-colorful-lp/scripts/apply-changes.mjs --plan <スクラッチパッド>/plan.json --target <出力先>/src/data/lpContent.js
```
- 変更するのは `changes` の項目の `title:`・`lead:` の1行だけ。「維持」「同じ」の項目は書き換えない。
- スクリプトが書き込み前に確認すること(1つでも満たさなければ書き込まず、終了コード 1):
  - 書き込み先が frontend/ 配下・複製元と同じファイルでない。
  - 書き込み先が、複製元と完全に一致している(複製直後の状態)。
  - 計画の変更前の値が、現在の frontend の値と一致している。
  - ブロック内で対象行がちょうど1つ見つかり、末尾が `',` の形式である。
  - 値は JS 文字列リテラルとして安全にエスケープする(`\`、`'`、改行、制御文字、U+2028/2029)。
  - 反映後に読み込み直し、値が異なるキーの集合が `changes` と完全に一致し、各値が期待値と一致し、差分の行が変更した行だけである。
- 終了コード 0 のあとも、手順8のうち次を確認する:
  - `diff -rq frontend/src <出力先>/src` の差分が `src/data/lpContent.js` だけ(変更0件なら差分なし)。
  - 設定ファイル、`index.html`、`public/` が複製元と一致したまま。
- 想定外の差分や終了コード 1 の場合は、内容を報告して停止する(`npm ci` に進まない)。

## 未確認として残すこと

ブラウザ確認を実施していない場合は、**未確認**として報告する。HTTP応答や文字列の含有確認だけで、ブラウザ表示を確認済みとしない。次はブラウザ・実画像での確認が必要である。
- ブラウザでの実際の表示(PC・SP 390px・375px)。変更した見出し・説明文の折り返し・はみ出し・行数の増減による見え方を含む
- 画像内テキスト(Hero・Members・最終CTA)と alt・資料の一致
- optimized の WebP と元画像の内容の一致
- アンカー移動時の位置(固定ヘッダーとの重なり)
- Opening・メニュー・Animation の動作
- 画像の width/height 属性と実寸のずれの影響

案件の要件に合わせて決める項目(応募リンクの有無、公開時の robots、正式な各URL、ナビの範囲)は、決定済みとして扱わず「今後決める事項」として報告する。

## 禁止事項

- `frontend/`、既存の出力フォルダ、`docs/01〜03`、`docs/06`、Input、`docs/archive/`、ZIP の変更
- 出力先の上書き・削除
- 14項目のうち、Input で「変更」と判定した項目以外の変更
- 14項目以外の変更(文章・画像・カード内容・リンク・色・Section の順序・番号・英字ラベル・`index.html`・設定ファイルを含む)
- 空文字・空白だけ・改行だけの値を「削除」とみなして反映すること、未指定を空文字として扱うこと
- 見出しだけあって値(コードブロック)が無い項目を、「未指定」として進めること
- CRLF の `\r` を値に残すこと、正規化のついでに空白や改行数を変えること
- CSV の検証エラー(`ok: false`)を無視して生成へ進むこと。CSV の文字列をコードとして実行すること。CSV の値の前後の空白・改行を削除すること。「維持」の行の入力内容を反映すること
- 改行の追加・削除・整形
- 対応範囲外の差分や判断不能な項目があるまま生成を進めること
- 既存サーバーの停止
- 既存素材の削除
- `npm ci` の繰り返し実行
- Commit・Push
- HTTP応答だけでの「表示確認済み」の報告
